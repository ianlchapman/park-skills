# park-tickets

Indicative ticket pricing for theme park visits: single-day and multi-day
tickets, season/annual passes, and add-ons (fast-track, parking, and
similar), including age-based pricing (adult/child/senior) where it applies.
Prices are hand-curated from public pricing pages and are **indicative, not
live** — always check `validity.lastChecked` / `validity.season` and tell
the user prices may have changed since then.

## Data location

One JSON file per ticket product in `data/`, named by ticket ID:
`data/<ticket-id>.json` (e.g. `data/alton-towers-1-day.json`).

Unlike `park-info` (one file per park), this data is **ticket-first**: a
single ticket can cover multiple parks (combo tickets, regional/chain
passes), so each file lists the park(s) it covers rather than being nested
under a single park.

Generated by an external pipeline from a hand-curated CSV. Don't hand-edit
these files.

## Finding relevant tickets

1. Resolve the park name(s) to slug(s) the same way `park-info` does
   (kebab-case, e.g. "Alton Towers" → `alton-towers`).
2. Grep `data/*.json` for that slug in the `parkSlugs` array to find every
   ticket that covers that park:
   `grep -l '"alton-towers"' data/*.json`
3. For "what tickets cover both X and Y" questions, grep for one park slug
   first, then filter that result set for files that also contain the
   second park's slug — a ticket covering both will match both greps.
4. If no files match a park slug, say ticket data isn't available for that
   park rather than guessing prices.

## File shape

```json
{
  "id": "merlin-annual-pass-premium",
  "name": "Annual Pass Premium",
  "operator": "Merlin Entertainments",
  "parkIds": [1, 2, 3],
  "parkSlugs": ["alton-towers", "thorpe-park", "chessington-world-of-adventures"],
  "type": "annual_pass",
  "numDays": null,
  "pricing": {
    "currency": "GBP",
    "adult": 225,
    "child": 180,
    "senior": 180,
    "childAgeMax": 11,
    "seniorAgeMin": 60
  },
  "validity": {
    "season": "2026",
    "lastChecked": "2026-09-01",
    "windowDays": 365,
    "notes": "Unlimited entry to all covered parks for 12 months from first use"
  },
  "confidence": "high",
  "notes": null
}
```

- `type`: `single_day` | `multi_day` | `season_pass` | `annual_pass` | `addon`.
- `addonType` (only present when `type` is `addon`): `fast_track` |
  `parking` | `photo_pass` | `meal_plan` | `other`.
- `pricing.child` / `pricing.senior` absent means no separate discounted
  price is offered — use `pricing.adult` for all ages.
- `validity.season` is the year/season the price is indicative of;
  `validity.lastChecked` is when it was last verified — these are
  deliberately separate, don't conflate them.
- `validity.windowDays`, when present, is how long the ticket is usable
  from purchase/first use (e.g. `180` = "valid any day within 6 months"),
  distinct from `validity.season`.
- `confidence`: `low` or `high` — treat `low`-confidence prices as rougher
  estimates and say so if asked for precision.

## Answering common questions

- **"How much is a 1-day ticket to X?"** Find ticket files covering X's
  slug with `type: "single_day"`. Report `pricing.adult` (and
  `pricing.child`/`pricing.senior` with their age bands if relevant),
  `pricing.currency`, and flag `validity.season`/`lastChecked` so the user
  knows how current the figure is.
- **"Is an annual pass worth it for X?"** Compare the `annual_pass`
  ticket's `pricing.adult` against the `single_day` ticket's price × number
  of planned visits — state the assumption (visit count) you're using.
- **"What tickets cover both X and Y?"** Use the two-park grep approach
  above; report each matching ticket's name, `type`, and price.
- **"How much extra for fast-track/parking at X?"** Find `type: "addon"`
  tickets for X's slug, filter by `addonType`, report the price and any
  `notes` (e.g. per-vehicle vs. per-person).
- **"What does a family of 4 pay at X?"** Sum the right `pricing.*` field
  per person by age against `childAgeMax`/`seniorAgeMin`, and say so
  explicitly rather than assuming a fixed "family price" unless a ticket
  with that name exists.

If a requested park has no matching ticket files, say ticket pricing isn't
available for that park rather than estimating a figure.
